1. Introduction

ArchCustomWidgets is a monorepo factory that produces installable widgets and services extending Caelestia (HyDE 3.x-based) on Arch Linux / Hyprland / Wayland. Units plug into an existing Caelestia setup: waybar modules, standalone widgets, and systemd user services.

Gold Rule

Simplicity first. The shortest thing that works. Bash over compiled languages. Copy over symlinks. No new dependency without justification. If a solution needs a paragraph to explain itself, it is too complex — rewrite it.

Stack

  • Primary language: bash (bash 5+, set -euo pipefail in scripts)
  • No framework, no build step, no node/rust/go in the unit path.
  • Exception: python3 allowed in helper scripts only when bash genuinely cannot express it (e.g., parsing complex JSON).

Repo Layout

factory/     # CLI scripts: scaffold, install, update, validate
widgets/     # widget units
services/    # service units
shared/      # theme bridge, common libs
openspec/    # specs and change proposals
docs/        # documentation

3. Unit Contract

Manifest Schema

The manifest.json file defines the unit identity and metadata. The schema is enforced by factory/validate against factory/manifest.schema.json.

Field Type Required Description
id string Yes Unit id, lowercase-kebab-case (^[a-z0-9]+(-[a-z0-9]+)*$).
type enum Yes widget or service.
description string Yes One-line description of what the unit does.
stack string Yes Primary implementation stack (e.g. bash).
entrypoint string Yes Path of the entrypoint script, relative to the unit directory.
deps array No System packages or external repos the unit depends on.
config object No Free-form unit configuration.

Contract Rules

  1. Copy install. Units install by COPYING files into ~/.config. Never symlinks.
  2. Idempotent. install.sh must be safe to re-run. No errors on repeated execution.
  3. Backup before overwrite. Never overwrite an existing user file silently: back it up to <target>.bak-<timestamp> first.
  4. Uninstall leaves no trace. install.sh --remove removes exactly what it installed. No orphaned files, no leftover services.

5. Install Model

Units install by copying files into ~/.config. The model is idempotent, reversible, and safe to re-run.

Install Steps

  1. Navigate to unit. cd <unit>
  2. Run installer. ./install.sh — copies files, enables services.
  3. Re-run is safe. Installer checks for existing files before overwrite; backs up to .bak-<timestamp>.
  4. Uninstall. ./install.sh --remove — removes exactly what was installed, leaves no trace.
  5. System-level units (e.g., vpn-surfshark) prompt for sudo only for system-level files.
  6. Services validated. systemctl --user enable --now + is-enabled / is-active checks pass.

Backup Rule

Never overwrite an existing user file silently. The installer always backs up to <target>.bak-<timestamp> before overwriting. Backups are excluded from git via .gitignore (*.bak-*).

6. Services & systemd

Naming Convention

All service units follow the pattern <vendor>-<unit>.service where vendor is acw.

User vs. System Units

Scope Unit Path Units
User (--user) ~/.config/systemd/user/ wallpaper, quickshell-watchdog
System (sudo) /etc/systemd/system/ vpn-surfshark (surfshark-connect / surfshark-disconnect)

Validation Commands

# User units
systemctl --user is-enabled acw-wallpaper-theme.service
systemctl --user is-active  acw-wallpaper-theme.service

# System units (sudo)
systemctl is-enabled surfshark-connect.service
systemctl is-active  surfshark-connect.service
Timer Units

The quickshell-watchdog service uses a 1-minute timer with WantedBy=timers.target to ensure it starts automatically with the system. The timer triggers the watchdog script, which checks if quickshell is running and restarts it if dead.

7. Theming Contract

Rule: Never Hardcode Colors

Every unit consumes the active wallbash / Caelestia palette through CSS variables or environment tokens. A unit needing its own colors exposes them as config, never as literals in code.

How It Works

Units reference the active theme via CSS variables (for waybar modules and widgets) or environment tokens (for bash scripts). The theme is managed by Caelestia's matugen pipeline, which generates palette files from wallpaper images.

Config Centralization

Per-unit configuration is centralized in either:

  • manifest.json config section — for structured config
  • env.conf at unit root — for simple key-value pairs

Palette Consumption

Waybar modules consume the palette via CSS variables (e.g., var(--accent)). Bash scripts consume it via environment tokens set by the Caelestia pipeline. No unit defines its own color literals.

8. Validation

Done Means 100% Functional

A unit is DONE only when ALL 7 checks pass. No partial validation. No "mostly working." Every check must succeed.

Validation Checklist

  1. bash -n clean. Every script in the unit passes bash -n (syntax check).
  2. manifest validates. manifest.json validates against the JSON schema via factory/validate.
  3. Clean install. install.sh runs successfully on a fresh target.
  4. Uninstall leaves no trace. install.sh --remove removes exactly what was installed.
  5. Service validation. For service units: systemctl --user is-enabled && is-active both succeed after install.
  6. Theme consumption. Unit consumes the current theme (visual check against active wallbash palette).
  7. Visual smoke test. For interactive/visual units: manual smoke test performed, noted in README.

factory/validate

The validation script scans both widgets/ and services/ directories. It checks:

  • manifest.json exists and conforms to schema
  • install.sh exists and is executable
  • Entrypoint script exists at declared path
  • No syntax errors in bash scripts

9. Lifecycle & OpenSpec

Lifecycle Steps

  1. Change proposal. A change is proposed in openspec/changes/. Each change has a proposal.md, design.md, and tasks.md.
  2. OpenSpec spec. The proposal drives a spec in openspec/specs/. Specs use delta-driven format with SHALL / MUST requirements and Scenario blocks.
  3. Factory scaffold. The factory tooling scaffolds a new unit directory from the spec.
  4. Implementation. Code is written to satisfy the spec requirements.
  5. Validation. The full 7-check validation pipeline runs.
  6. Archive & sync. Completed specs and changes are archived. The codemap is updated.

Canonical Spec

The canonical unit spec lives at openspec/specs/factory-units/spec.md. All new units must trace back to a requirement in this spec or a new spec derived from it.

Spec-Driven Development

OpenSpec uses a schema-driven approach (openspec/config.yaml: schema: spec-driven). Specs use formal language: SHALL for mandatory requirements, MUST for absolute requirements. Each requirement has associated Scenario blocks for validation.

10. Security & Publishing

Gitignore Exclusions

The following files are excluded from version control to prevent sensitive data and local state from leaking into public repositories:

Pattern Reason
services/vpn-surfshark/src/nftables.conf Live firewall rules (network topology) — untracked, stays local. Fresh clones lack this file; install.sh of vpn-surfshark unit needs the real file.
**/tasks.txt Local user data / state files
**/countdowns.txt Local user data / state files
**/.state Local user data / state files
**/.current_style_index Local user data / state files
*.bak-* Backup files created by install.sh during overwrite
.opencode/node_modules/ Local tooling dependencies
.opencode/package.json Local tooling config
.opencode/package-lock.json Local tooling lockfile
.opencode/bun.lock Local tooling lockfile
Secrets Never Shipped

WireGuard configs (/etc/wireguard/surfshark.conf), API keys, tokens, and credentials are never part of this repository. They remain outside scope. The vpn-surfshark unit expects the user to provide their own WireGuard config at the expected system path.

GitHub-Ready Without Leaks

The repository is safe to publish publicly. All sensitive data, state files, backups, and local tooling artifacts are excluded via .gitignore. The only file that could theoretically leak network topology is nftables.conf, which is explicitly untracked.

Fresh Clone Impact

When cloning this repository fresh, the vpn-surfshark unit will be missing its nftables.conf file. The install.sh script for this unit will fail unless the user provides the real firewall rules file. This is by design: the file contains live network topology and must never be committed.
